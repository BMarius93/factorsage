# Legal, privacy and consumer-protection architecture

How the legal surface is implemented, as it exists. `docs/legal/` holds the specification this
was built from and the register of facts still outstanding; this document describes the code.

> **Status.** The mechanics below are implemented and tested. **The wording is not approved**:
> every document is `DRAFT`, every operator fact is unresolved, and a release build refuses to
> compile while either is true. Nothing here is a legal opinion or a statement of compliance.

Read `../../docs/legal/README.md` first for the product intent, then
`../../docs/legal/owner-inputs-and-review.md` for what is still missing and who owns it.

## 1. One registry, six documents

`packages/contracts/src/legal-documents.ts` holds the immutable, versioned text of every public
document: Terms, Privacy, Cookies, Risk Disclosure, Cancellation & refunds, and Contact. Each has
exactly one canonical route, one version, one effective date, one status and one **content
digest**.

The digest is SHA-256 over `canonicalLegalDocumentText(document)` — the kind, the version, and
every heading, paragraph, list entry and pending marker in order. It is generated by
`pnpm legal:hashes` into `packages/contracts/src/legal-document-hashes.ts` and recomputed by
`packages/contracts/src/legal-documents.test.ts`, so **editing the copy without regenerating fails
the build**. That is what makes a stored acceptance resolve to the exact text it was given for
rather than to whatever the copy has since become.

Operator facts are `{{PLACEHOLDER}}` markers, never values. The repository is public: committing
the owner's real identity would publish it and inventing one would be worse. An unresolved marker
renders as a visible draft badge naming the fact and its owner-input entry, and blocks a release.

**Deliberately absent from the copy**, and asserted absent by a test: any claim that a disclaimer
removes liability, any blanket "no refunds", any waiver, any retention period, any named provider,
and any conclusion about consumer or financial-regulatory classification.

## 2. Presentation

| Surface                                                        | What it is                                                                                                                                                                                                                |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/web/src/features/legal/components/LegalDocumentPage.tsx` | The one renderer for all six documents. A server component with no API call and no session dependency, so it renders for a Guest, an expired session and a user who has declined.                                         |
| `SiteFooter.tsx`                                               | One footer, rendered by `AppShell` for product routes and by `AuthCard` for the sign-in screens. Carries the legal destinations, the operator's identity and the standing short disclosure.                               |
| `DisclosureNote.tsx`                                           | The contextual disclosures, from `LEGAL_DISCLOSURES` in `@intrinsic/contracts` so there is one wording per claim. Placed on the Dashboard signals, a Monitor's signals, a backtest result and a stock's intrinsic values. |
| `SubscriptionDisclosure.tsx`                                   | Renewal, statutory withdrawal and nonconformity, kept apart. On `/pricing` and `/billing`.                                                                                                                                |

The routes live inside the `(app)` route group, so they wear the product's own chrome and are
listed in `GUEST_ROUTE_PATTERNS`. They are statically rendered.

The disclosure copy is written against what the engine actually does: an active signal may be
**latched** rather than newly fired, a pending setup is not a signal, a backtest includes only the
costs its own methodology describes, and an intrinsic value is a model output. No financial
formula, signal semantic, plan limit or reconciliation path was changed by this work.

## 3. Terms acceptance

### What is recorded

`LegalRecord` is append-only: `userId`, `documentKind`, `documentVersion`, `documentHash`,
`record`, `surface`, `recordedAt`, unique on `(userId, documentKind, documentVersion)`. There is no
update path and no writer that changes a row after insert — `createMany({ skipDuplicates: true })`
is the only write, which is also the whole idempotency story.

One acceptance writes three rows: **Terms** and **Risk Disclosure** as `ACCEPTED` (the Terms say
the Risk Disclosure forms part of them, and recording it separately is what makes that auditable),
and **Privacy** as `NOTICE_PRESENTED`. A privacy notice is information; recording it as an
acceptance would misrepresent it as a blanket consent to every processing purpose.

IP address and user agent are deliberately **not** collected for this purpose: it was not approved
and has no retention policy (`O5`), and the authenticated account is already the thing the record
is about.

### Where acceptance happens

| Path             | Surface             | Where                                                        |
| ---------------- | ------------------- | ------------------------------------------------------------ |
| Email            | `EMAIL_ACTIVATION`  | `POST /auth/verify-email`, inside the redemption transaction |
| Google           | `GOOGLE_ONBOARDING` | `POST /legal/acceptance`, after the callback                 |
| Existing account | `EXISTING_ACCOUNT`  | `POST /legal/acceptance`                                     |

**Registration records nothing.** `POST /auth/register` takes an address and nothing else and
anybody can submit somebody else's, so binding an acceptance to it would record a contract on
behalf of a person who has not been asked. A `termsVersion` posted to registration is ignored
exactly like a `password` is. The activation form is the first point on the email path at which
the mailbox holder has proven the address is theirs, and the acceptance is written in the same
transaction that installs the password — so an activated account without its acceptance is not a
reachable state, and a rejected version activates nothing.

The **surface is resolved server-side** from persisted state (`LegalService.resolveSurface`) and is
never read from the request: evidence a caller can choose is not evidence.

`REQUIRED_TERMS_VERSION` is deliberately a separate constant from `TERMS.version`. A typo fix or a
Privacy update bumps a document's own version without moving it, so only a **material** change
sends existing customers through the acceptance screen. Nothing backfills a historical user as
having accepted.

### Enforcement

`LegalAcceptanceInterceptor`, registered globally by `LegalModule`. An **interceptor** for the same
ordering reason as `RateLimitInterceptor`: Nest runs enhancers global → controller → method, so a
global _guard_ would run before `CookieAuthGuard` and see no session at all.

It costs no extra query. The acceptance lookup rides on the `SELECT` the cookie guard already
issues (`TERMS_ACCEPTANCE_SELECT` in `users.service.ts`), so the acceptance state is read on the
same row, in the same statement, as the identity it is about, and reaches the interceptor on
`request.legalAcceptance`. Its absence on an authenticated request is treated as "not accepted", so
a guard that forgets to set it fails closed.

A refusal is `403` with `LEGAL_ACCEPTANCE_REQUIRED` and `requiredTermsVersion` — never `401`, which
would make every client sign the user out of the very screen that fixes it. Guests are never
gated.

**Every mounted route is gated by default.** Exemptions are declared with
`@LegalAcceptanceExempt(reason)` and pinned _exactly_ by
`apps/api/src/legal/legal-acceptance-coverage.test.ts`, because both failures are dangerous: an
extra exemption is a hole, and a missing one traps a paying customer. The three legitimate classes
are authentication itself, the rights a declining user keeps, and callers that are not a user.

`GET /market-overview` carries no session guard at all, so the gate has no session to read and it
answers identically for everyone. The coverage suite states that rather than leaving it to be
mistaken for a bypass later.

### The web side

`LegalAcceptanceProvider` probes `GET /legal/acceptance` once per session; `LegalAcceptanceGate`
renders the acceptance panel **in place of** a gated route, keeping the URL so accepting returns
the user where they were going. It is presentation only, and it **fails open**: a failed probe
renders the route, because locking somebody out over a timed-out request gains nothing when the
server refuses every gated request anyway.

`isReachableWhileTermsOutstanding` is the presentation half of the server allowlist, pinned by its
own test. Signing out is not on it because it is not a route: the account menu lives in the topbar,
outside the gate.

## 4. Browser storage and consent

The inventory is `STORAGE_INVENTORY` in `@intrinsic/contracts`, verified in a browser rather than
by searching the source, and `docs/legal/storage-inventory.md` records the method and the
observations. The `/cookies` page renders the policy **and** the table from that same constant, so
the published policy is the application's own inventory.

Two findings decided the design:

- the guest recent-securities key is a **convenience**, not strictly necessary, so it is optional
  and gated. The product works without it;
- the application loads nothing from a third-party origin at runtime — fonts are self-hosted by
  `next/font`, there is no analytics SDK, no Stripe.js and no Google script. Google and Stripe run
  on their own origins when a user is redirected there, and the local control explicitly does not
  claim to govern them.

Because one optional purpose exists, a consent control is required. `OPTIONAL_STORAGE_EXISTS` is
computed from the inventory: if the product ever stops writing optional storage the banner
disappears rather than becoming a request for permission it does not need.

The rules, in `storage-consent.ts` and `use-storage-consent.tsx`:

- **undecided is never permission.** Every read answers `null` for "no valid choice", and the
  provider reports `decided: false` until an effect has read the store — so the window between
  server render and that effect can only fail _closed_;
- **a blocked store fails safely.** Every access is wrapped; a throw resolves to undecided;
- **a version change invalidates the choice.** A record for a different `STORAGE_CONSENT_VERSION`
  is not migrated and not honoured;
- **withdrawal is the same single action as granting**, in the same place, and removes the optional
  key it wrote — without touching the session cookie, the consent record or anything else;
- **cross-tab**: a change elsewhere arrives through the `storage` event.

`RecentSecuritiesProvider` holds a Guest's recents **in memory** before a choice and after a
refusal, so the feature works and nothing reaches the device. The banner is `position: sticky`
rather than `fixed`, as the last child of the shell: a fixed bar would permanently cover the legal
footer, making the links to the very policy it is about unclickable until somebody answered it.

## 5. Requests, and what the product will not decide

`LegalRequest` records a `PRIVACY_REQUEST`, `WITHDRAWAL`, `NONCONFORMITY` or `SUPPORT` submission
with a random reference, the submitter's own words and the server's submission time. `RECEIVED` is
the only status this implementation writes.

`LegalRequestForm` gives every kind the shape the consumer rules ask a withdrawal function to have:
identification from the authenticated session, a review step, a confirmation, and an immediate
durable receipt. "Durable" is met three ways — on screen, saved as a plain-text file, and
retrievable later from the account's own history — and **not** by email, because there is no
approved monitored mailbox to send from (`O2`). A promised confirmation that never arrives is worse
than saying where the confirmation is.

**Submitting is not deciding.** Nothing here calculates a refund, waives a right, erases data or
touches a subscription. Whether a statutory right applies, when it runs and what may lawfully be
deducted are outstanding counsel questions (`O7`), and software that guessed them would assert a
legal outcome nobody has made. Any eventual refund goes through the existing Stripe gateway and
`BillingReconciliationService`; `User.plan` is untouched by anything in this slice.

Cancelling a renewal is deliberately **not** duplicated as a form: it is a billing action, it
already exists in the hosted customer portal reached from Billing, and a second control that looked
like one is exactly how somebody ends up believing they exercised a statutory right when they
stopped a renewal.

## 6. Release readiness

`legalReleaseReadiness()` computes the blockers from the code: every `requiredForRelease` owner
fact that is unresolved, and every document still `DRAFT`.

- `pnpm legal:check` reports them and exits non-zero. It is **not** part of `pnpm lint`/`test`/
  `build`: a draft page must stay reviewable locally, and a check that broke `pnpm dev` is one
  somebody switches off.
- `apps/web/src/lib/legal-release.ts` fails `next build` when `FACTORSAGE_RELEASE_BUILD=true`, the
  same flag that already requires a public API URL. Local builds, CI and the validation gate are
  unaffected.

Approving a document means changing its status **and** its version, which changes its digest, which
the contracts test recomputes — so the gate cannot be satisfied by flipping a flag.

## 7. QA personas

`seedQaUsers` records synthetic acceptance for every persona with the `EXISTING_ACCOUNT` surface.
Without it every persona would land on the acceptance screen and every browser journey would be
testing that screen instead of its own subject. It is a property of the seeder, not a bypass: there
is no production switch, no header and no route that skips the gate, and a spec that wants to see
the gate creates or clears its own account. `pnpm qa:reset` clears a persona's `LegalRequest` rows
and deliberately keeps its acceptance.

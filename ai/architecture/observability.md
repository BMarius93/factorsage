# Observability

## Goal

IntrinsicValue must make production failures diagnosable from structured logs without requiring code changes or reproducing the exact request locally.

`@intrinsic/observability` is the canonical server-side logging and correlation package. API, worker, stock-data, FMP adapters, database adapters, Redis/cache code, and future queue integrations should use it rather than creating independent logging conventions.

## Log levels

`LOG_LEVEL` is read from the shared application configuration and supports:

```text
fatal
error
warn
info
debug
trace
silent
```

Normal guidance:

- production: `info`
- local development: `debug`
- targeted short-lived diagnostics: `trace`

`info` must be useful enough to follow major lifecycle events without enabling high-volume diagnostics.

## Structured events

Logs are newline-delimited JSON. Prefer stable event names over prose-only messages.

Examples:

```text
api.bootstrap.started
api.started
http.request.started
http.request.completed
http.request.aborted
stock.hydration.started
stock.hydration.completed
stock.hydration.failed
fmp.request.completed
backtest.started
backtest.completed
worker.stopping
```

For meaningful operations, log lifecycle boundaries and include `durationMs` on completion or failure when useful. Do not log every function entry/exit.

## Correlation context

The standard context fields are:

- `requestId`: unique ID generated by the API for one HTTP request.
- `correlationId`: ID used to connect one logical operation across layers/processes.
- `actorUserId`: internal ID of the authenticated user that initiated the operation, when available.
- `runId`: durable execution/run identifier when a domain execution exists.
- `jobId`: queue/background-job identifier.
- `symbol`: stock symbol for stock-specific work.
- `component`: logical emitting component such as `http`, `stock-data`, `fmp`, or `redis`.

The API creates `requestId` and `correlationId` at the HTTP boundary. Authentication adds `actorUserId` after the user is resolved. `AsyncLocalStorage` propagates this context inside the same Node process.

Do not pass context parameters through every business method merely for logging when the operation remains inside the same process.

## Process boundaries

`AsyncLocalStorage` does not cross processes.

When API enqueues work for the worker, the job contract must explicitly carry the relevant correlation data, for example:

```text
correlationId
actorUserId
runId
jobId (or queue-native job ID)
```

The worker recreates the log context before executing the job. From that point, nested worker/stock-data/FMP/database calls inherit the context normally.

A background/system-created job may have no `actorUserId`; do not invent one.

## User correlation and privacy

Use `actorUserId` as the normal user correlation key. Do not log the user's email simply to make logs searchable.

Never log:

- passwords or password hashes
- cookies or `Set-Cookie`
- authorization headers
- JWT/session tokens
- API keys
- Stripe/FMP secrets
- raw credentials
- complete sensitive request or response bodies

The logger defensively redacts common secret-bearing keys, but callers remain responsible for choosing safe fields. Redaction is a final safety net, not permission to log arbitrary payloads.

## Errors

Failures should include the original error object so name/message/stack remain available, plus operational identifiers required to answer:

- what operation failed?
- for which request/job/run/symbol?
- which external component was involved?
- how long had the operation been running?

Logging must not change error semantics. Do not catch-and-ignore errors solely to produce a log line.

## Stock-data expectations

As stock-data code is changed, add structured operational events at high-value boundaries such as:

- security cache/DB/provider resolution
- hydration cache READY hit/miss
- hydration/refresh start, completion, and failure
- durable coverage calculation and missing FMP deltas
- FMP request/retry/rate-limit outcomes
- DB persistence boundaries
- derived daily/weekly/intrinsic calculation boundaries
- Redis publish/eviction/recovery operations

Use `debug` for cache hits, row counts, ranges, retry detail, and other high-cardinality operational detail. Keep `info` focused on meaningful lifecycle outcomes.

## Event evolution

Treat event names and standard field names as operational contracts. Rename them deliberately because dashboards, searches, alerts, tests, and support procedures may rely on them.
